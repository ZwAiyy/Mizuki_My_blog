我每天要做一件重复的事：打开浏览器 → 进 Lark 多维表格 → 找到昨天那几行 → 把消耗和利润抄出来发到群里。

这件事大概花 3 分钟，但它每天都要发生，而且**依赖我本人记得做**。于是决定自动化。这篇文章记录整个过程——包括三条走不通的死路，和最后那条走通的路。

## 先说结论

最终方案是：**用 Playwright 复用我自己的登录 Cookie，直接调 Lark 多维表格网页端在用的两个内部接口**，拿到原始 JSON 后在本地按日期汇总、算环比，再推一张卡片到 Lark 群。

```
视图链接 (/base/... 或 /wiki/...)
   │
   ▼
解析出 app_token / table_id / view_id
   │
   ├─► clientvars 接口 → 字段定义、视图顺序、视图筛选条件   （缓存 7 天）
   │
   └─► records 接口   → gzip+base64 载荷 → recordMap / formulaInfo
            │
            ▼
      本地套用视图筛选 → 字段 ID 翻译成列名 → 按日期分组求和
            │
            ▼
      渲染成 markdown 分段 → Lark 群机器人 Webhook
```

整个过程**不解析网页、不模拟点击**，每天只发 3~4 个很轻的 HTTP 请求。

## 约束：为什么"正路"走不通

自动化读多维表格，正常思路是走开放平台 API。但这条路有个前置条件：

> 自建应用必须被**表的所有者**添加为文档协作者，才能读这张表。

而我对这个表**只有查看权限**。这意味着三件事同时不可行：

| 想做的 | 为什么不行 |
|--------|-----------|
| 开放平台 API | 自己加不了协作者，得求表所有者 |
| 表内置的「自动化」定时推送 | 新建自动化属于**编辑**操作 |
| 自己建一个「昨天」筛选视图 | 同样是编辑操作 |

查看权限能做的事只有一件：**用浏览器打开它看**。所以方案只能建立在"我能看到什么"之上。

## 第一条死路：表体是 canvas 画的

既然只有浏览器这条路，那就写浏览器自动化。Playwright 复用登录态，打开页面，读 DOM——听起来顺理成章。

结果抓下页面现场一看，傻眼了：

```
元素总数       1373
canvas 数      1          ← 整个表体就是这一块画布
role=grid 数   0          ← 没有任何表格语义元素
table 数       0
body.innerText 长度 = 284  ← 全是侧边栏和工具栏的文字
```

那张 1.1 MB 的 HTML 里，我要找的列名「实际消耗」「总利润」**出现了 0 次**。整个表体长这样：

```
<canvas faster="1" width="1360" height="852">
   └ div.faster-view
      └ div.bitable-table-view--content
         └ div.bitable-container
```

更绝望的是键盘这条路也不通：点了表格、按 `Ctrl+A` 再 `Ctrl+C`，剪贴板内容**一个字都没变**（还是我之前复制的一段命令行）。

**结论：文字是画在画布像素上的。** DOM 里没有文本节点，键盘事件也不进表格。所以"读 DOM"和"读剪贴板"在这张表上不是"选择器没调对"，是方向本身就不对。

那数据总得从哪来吧？前端能画出来，说明数据一定已经到了浏览器里。

## 转机：看前端自己是怎么取数的

思路很简单——**监听页面自己发出的所有请求**，按路径聚合，立刻看到：

```
1  /space/api/v1/bitable/<app_token>/records
1  /space/api/v1/bitable/<app_token>/clientvars
```

前端要画表格，就必须先把数据取到浏览器里。找到那个请求，照着调就行了。

这两个接口都是普通 `GET`，**只认 Cookie，没有 CSRF 校验**：

| 接口 | 返回 |
|------|------|
| `clientvars` | 表结构：字段 ID → 名称/类型/选项、视图配置、视图筛选条件 |
| `records` | 记录数据，`data.records` 是 **gzip + base64** |

更进一步，我用 Playwright 的 `context.request` 来发请求，而不是在页面里 `fetch`——它和浏览器上下文**共享同一个 Cookie 罐**，于是**连页面都不用打开**，直接发 HTTP。这也顺带解决了后面要说的限流问题。

## 数据格式：一层套一层的"套娃"

真正的工作量在于把数据解开。它的格式设计得相当"紧凑"。

### 第一层：信封

```json
{"code": 0, "msg": "success", "data": { ... }}
```

### 第二层：载荷不是对象，是字符串

```json
"data": {
  "encoding": 0,
  "records": "H4sIAAAJbogA/+x9X2/rSJbfV1lwJoMdrJvNKpJF..."
}
```

`H4sI` 就是 gzip 的魔数（base64 编码后的样子）。所以是三步解：

```python
raw   = base64.b64decode(blob)      # base64 → 字节
plain = gzip.decompress(raw)        # gzip   → JSON 字节
data  = json.loads(plain.decode("utf-8"))
```

### 第三层：记录本体

解压后的顶层有一堆键，真正要的是两个：`recordMap`（记录数据）和 `formulaInfo`（公式结果）。

`recordMap` 是三层结构，而且**键是字段 ID 不是列名**：

```json
"recordMap": {
  "recvXXXX": {
    "fldA": {"value": 1372.73,  "modifiedTime": 1787918431},
    "fldB": {"value": 1787068800000, "modifiedTime": 1787918431},
    "fldC": {"value": [{"type": "text", "text": "项目A"}]},
    "fldD": {"value": ["optXXXX"]}
  }
}
```

列名要从 `clientvars` 的 `fieldMap` 里反查：

```json
"fieldMap": {
  "fldA": {"name": "实际消耗", "type": 2},
  "fldB": {"name": "日期",    "type": 5},
  "fldC": {"name": "项目",    "type": 1}
}
```

所以"中文列名 → 字段 ID → 值"需要两步映射。

### 不同类型的值，编码完全不同

这是最容易翻车的地方，我把实测结果整理成表：

| type | 含义 | 原始值 | 要做的事 |
|------|------|--------|----------|
| 1 | 文本 | `[{"type":"text","text":"项目A"}]` | 富文本数组，得拼 `text` 字段 |
| 2 | 数字 | `1372.73` | 直接用 |
| 3 / 4 | 单选/多选 | `["optXXXX"]` | 是 **option id 不是显示名**，要查 `property.options` |
| 5 | 日期 | `1787068800000` | 毫秒时间戳，**且有时区陷阱**（下文） |
| 20 | **公式** | **不在这** | 在 `formulaInfo`，见下 |

### 公式字段：值藏在另一个地方，还要再解一层

「总利润」是公式字段（type=20）。它的值**不在 `recordMap` 里**，而在：

```json
"formulaInfo": {"fieldMap": {
  "fld0XXX": { "recvXXXX": {
    "value": "{\"bus_type\":[202],\"data\":[233.5731]}",   ← 又是一段 JSON 字符串
    "ext": ""
  }}
}}
```

注意 `value` 本身是**一段 JSON 字符串**，要再 `json.loads` 一次，然后取 `data[0]`。`bus_type` 标记结果类型：`201` = 字符串结果，`202` = 数值结果。

这个合并逻辑我没敢凭感觉写，用了一段独立实现交叉验证：对全表 543 条记录逐条断言 `总利润 == 增值 + 服务费利润`，**543 条全部一致，0 条例外**。

### 日期的时区陷阱：碰巧对，比明确错更危险

日期字段的值是 epoch 毫秒，看起来 `datetime.fromtimestamp(ms/1000)` 就完了。但我发现一个很反直觉的事实——全表 543 个日期值：

```
ms % 86400000 的取值集合 = {57600000}    ← 只有一种取值
57600000 ms = 16 小时
```

也就是说 Lark 把「某天零点」表示成了 **`UTC 前一日 16:00`**，即 **UTC+8 的零点**。

后果是：我的机器恰好是 UTC+8，用 `fromtimestamp()`（本机时区）**碰巧正确**；一旦这套脚本挪到 UTC+0 的服务器上，**所有日期整体偏一天**，日报会安静地报错数字而不报任何错。

"碰巧对"比"明确错"可怕得多。所以代码里显式写死偏移量：

```python
def _ms_to_iso(value, tz_offset_hours=8.0):
    stamp = float(value) / 1000.0
    shifted = dt.datetime.fromtimestamp(stamp + tz_offset_hours * 3600.0,
                                       tz=dt.timezone.utc)
    return shifted.date().isoformat()
```

## 又踩的两个坑

数据格式之外，接口本身还有两个坑，都是**静默失败**型的。

### 坑一：参数名必须大写

`records` 接口的表/视图参数，写成驼峰 `tableId` / `viewId` 会被**静默忽略**：

| 参数写法 | 返回 | 字段匹配 |
|----------|------|----------|
| `tableId=...&viewId=...` | 65 条 | 与目标表 **0 个**匹配 |
| `tableID=...&viewID=...` | 591 条 | 全部匹配 |

它不报错，而是**转而返回这个 base 里第一张表的数据**。我第一张表恰好就是它 base 的第一张表，于是用错参数也一直是对的；直到接第二张表才暴露——返回的根本不是我要的表，字段 ID 一个都对不上。

这种"在 A 场景下看起来正常，到 B 场景才炸"的 bug 最难排查。

### 坑二：视图筛选，接口不套用

`records` 返回的是**整张表**，不应用视图自己的筛选条件。而我用的视图恰好带了一个筛选（排除若干项目），不本地算这个条件，数字会明显偏大：

```
视图筛选：1 个条件（and），保留 517 条、排除 74 条
```

所以我在本地实现了筛选求值。这里有一条我给自己定的**安全原则**：

> 遇到不认识的运算符，**告警并按整表计算**，绝不静默返回一个错的数。

宁可让用户看到"有条件没算上"，也不给他一个看起来正常、实际偏大的数字。

### 附带一坑：wiki 链接的 token 不是 app_token

`/wiki/<node_token>` 里的 token 是知识库节点 ID，**不能**当 app_token 用，直接返回 `code=3 Not Found`。真实 app_token 是另一个值。

解法：首次打开一次页面，监听它自己发出的 `/bitable/<token>/...` 请求，配合 URL 里的 `table=` 参数确认是目标表，把 token 抓出来**缓存**。一个 wiki 只解析一次，之后零成本。

## 工程化：让它能长期跑

### 缓存与请求预算

| 缓存 | 有效期 | 理由 |
|------|--------|------|
| 字段结构（fieldMap） | 7 天 | 列名/类型几乎不变 |
| wiki app_token | 永久 | 节点与表的对应关系不会变 |

于是日常运行每天只发 **2 次 records 请求**。

缓存我加了格式版本号。这是被真实教训逼出来的：早期版本存的是 `filter_active` 布尔值，后来改成了 `filter_info` 对象，如果直接读旧缓存，筛选会**静默失效**。现在版本号不匹配就自动丢弃重拉。

### 限流：区分"被限流"和"登录失效"

测试期间我反复探测，被 Lark 限流了，症状很迷惑——页面根本打不开，Chrome 停在 `chrome-error://chromewebdata/`。这不是登录问题，是网络层被拒。

所以代码里专门做了区分，并给出**可操作**的提示：

- 页面打不开 → "被限流了，等 10~30 分钟，期间别反复重跑"
- 出现登录表单 → "跑一次 login_once.py"

关键的一条设计是：`NetworkBlocked` 异常**直接向上抛，不再降级重试**。页面都打不开，换别的取数策略只会加重限流。

### 部分失败不拖垮整体

接了两个数据源之后，某一个挂了不应该让整张卡发不出去。所以单个源失败时，卡片里那一段渲染成 `_取数失败：..._`，其余照常推送；只有**全部失败**才不推，并以非 0 退出码结束（方便定时任务告警）。

### 测试：用独立实现交叉验证自己

这套脚本完全不联网也能测，98 项断言。其中最有价值的一层是**真实快照回放**：

把之前抓下来的真实数据落盘 → 用**生产代码**跑一遍 → 同时用**另一段独立写的实现**重算 → 逐天比对。

```
ok   全部 106 天都与独立重算一致
```

这一层同时验证了「公式字段合并 + 时区换算 + 按天分组」三件事。用独立实现交叉验证，是为了避免"用同一段错误逻辑验证自己"——那是最舒服也最没用的测试。

### 一个差点误判的插曲

联调时我发现某天的消耗从 1.8 万跳到了 18.9 万，差点当成 bug 深挖。逐条对比新旧两次数据后确认：**数据本身被补录了**——8 条里有 5 条的消耗原本是空的，后来被填上了；另外 3 条**逐位一致**。

遇到数字对不上，先怀疑数据、再怀疑口径、最后才怀疑代码。顺序反了会浪费很多时间。

## 局限，和它的固有代价

必须诚实地说清楚这套方案的软肋：

1. **内部接口不是公开契约**。Lark 改版可能导致路径、参数或载荷格式变化。我保留了剪贴板/状态栏两条降级路径，但它们对 canvas 渲染的表体无效。
2. **依赖本机登录态**，几周过期一次，需要重登。
3. **会被限流**，被限流时只能等。
4. **视图筛选只支持常见运算符**，用到不支持的会告警并按整表计算。

**长期更稳的做法**还是去要权限：让表的所有者把自建应用加为协作者，改用官方 API——那是公开契约、有文档、不需要浏览器。这套脚本的下游（按日期汇总、算环比、渲染卡片、推送）到时候完全复用，只换掉最前面取数的那一小段。

---

写在最后：这件事最有意思的地方不是"爬到了数据"，而是**约束条件反过来指明了方向**——正因为没有 API 权限、正因为表体是 canvas、正因为日期存的是 UTC+8 的毫秒，每一步该怎么做才变得清晰。遇到"看起来没法自动化"的东西，先把它不能自动化的原因逐条列出来，答案往往就藏在里面。
